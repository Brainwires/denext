denext runs your project on its own build of Deno: the CLI, `denort` (what `deno compile` and
`denext build --compile` build onto) and the Deno Desktop runtime, all from the public
[Brainwires/deno](https://github.com/Brainwires/deno) fork. It is upstream Deno 2.9.8 plus the
additions below. You don't install it: denext downloads the build it pins, checks its SHA-256 and
runs every command that needs Deno on it ([denext's Deno toolchain](/docs/toolchain)).

This page lists what the fork adds that you can see or use. Internal fixes (crash fixes, security
patches carried ahead of upstream, test and CI changes) are described in the fork's
[DENEXT.md](https://github.com/Brainwires/deno/blob/development-denext/DENEXT.md). In the tables,
`denext.N` is short for runtime `2.9.7-denext.N`, the builds before the fork took its own
`3.0.0-rc.N` version.

## Which runtime am I on?

From runtime `3.0.0-rc.3` the runtime says whose it is. Upstream Deno releases a `3.0.0` too, so
the version number alone doesn't tell them apart:

```ts
if (Deno.build.denext) {
  console.log(`denext's Deno ${Deno.build.denext}`); // "3.0.0-rc.5"
} else {
  console.log("upstream Deno: Deno.SQL and the other additions are not here");
}
```

```text
$ deno --version
deno 3.0.0-rc.5 (stable, release, aarch64-apple-darwin)
v8 15.0.245.2-rusty
typescript 6.0.3
denext 3.0.0-rc.5 (Brainwires)
```

| What                       | Detail                                                                                                                                                                                            | Since        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `Deno.build.denext`        | The runtime's version, a string, in the main thread and in workers. `undefined` on stock Deno.                                                                                                    | `3.0.0-rc.3` |
| `deno --version` last line | `denext <version> (Brainwires)`; `deno -V` stays one line.                                                                                                                                        | `3.0.0-rc.3` |
| `Deno.version.deno`        | The fork's own version (`3.0.0-rc.5`), also in the user agent (`Deno/3.0.0-rc.5`). Before `3.0.0-rc.1` it was `2.9.7-denext.N`.                                                                   | `3.0.0-rc.1` |
| `deno upgrade`             | Refuses to run in a release build, and the background update check is off: upstream's channels would replace the fork with stock Deno. Use `denext upgrade` or `denext toolchain install`.        | `3.0.0-rc.1` |
| Release channel            | `deno --version` says `stable`, the channel of the Deno release the build is made from (2.9.8). `npm` `engines.deno` ranges are checked against that release, not against the prerelease version. | `3.0.0-rc.1` |

The versions sort in release order by semver: `2.9.7-denext.1` … `2.9.7-denext.22`, then
`3.0.0-rc.1`, `3.0.0-rc.2`, … `3.0.0`. denext 4.x pins `3.0.0-rc.5`; `3.0.0-rc.6` is released and
the rows marked "rc.6" below need it. Before the marker (`3.0.0-rc.2` and earlier) denext
recognises its runtime by the version alone ([Versions](/docs/toolchain#versions)).

**Required from denext 5.0.** denext runs only on this runtime, `3.0.0-rc.5` or later: the
stock-Deno escape hatch (`DENEXT_DENO=stock`) and every stock-Deno fallback are gone, so everything
on this page from `3.0.0-rc.5` and earlier — `Deno.SQL`, the lifecycle-script jail, the idle trim,
the direction-split network flags, native TypeScript 7 — is always there. A `DENEXT_DENO=<path>`
must be a build of it (told by the identity line above); anything else is refused with the fix
([Upgrading to 5.0](/docs/toolchain#upgrading-to-50)).

## JavaScript and TypeScript APIs

### `Deno.SQL` and `Deno.sql`

A built-in SQL client for Postgres and SQLite with Bun's `Bun.sql` surface and no npm. Every
interpolated value is sent as a parameter, never spliced into the text. Since `2.9.7-denext.14`, in the CLI archive from `2.9.7-denext.15`; stock Deno has none
(its nearest is `npm:postgres`). The Postgres side of [Database](/docs/database#postgres) and
`postgresClient()` run on it.

```ts
const sql = new Deno.SQL(Deno.env.get("DATABASE_URL")!, { max: 10 });
const users = await sql`select id, name from users where id = ${id}`;
await sql`insert into users ${sql({ name: "Ada" })}`;
await sql.begin(async (tx) => {
  await tx`update accounts set balance = balance - ${n} where id = ${from}`;
  await tx`update accounts set balance = balance + ${n} where id = ${to}`;
});
```

| API                                                                             | What                                                                                                                                                                                                                                                                                  | Since        |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `new Deno.SQL(url \| options)`                                                  | A pooled client: `postgres://…`, `sqlite://…`, `file:…`, `:memory:` or `{ adapter: "sqlite" }`. Options: `max`, `idleTimeout`, `maxLifetime`, `connectionTimeout`, `prepare`, `bigint`, `tls: { ca, servername, rejectUnauthorized, cert, key }`, `onconnect`, `onclose`, `onnotice`. | `denext.14`  |
| `Deno.sql`                                                                      | A default client created on first use from `POSTGRES_URL`, `DATABASE_URL`, `PGURL` or `PG_URL` (env permission); `PG*` variables fill missing fields only when env access is already granted.                                                                                         | `denext.14`  |
| `` sql`…` ``                                                                    | A query: a promise of the rows, plus `.values()`, `.raw()`, `.simple()`, `.cursor(n)`, `.cancel()`; `for await (const row of sql`…`)` reads a server-side cursor.                                                                                                                     | `denext.14`  |
| `sql(object \| objects, ...columns)`, `sql(array)`, `sql("name")`               | Helpers chosen by the keyword before them: INSERT, `UPDATE … SET`, VALUES, IN, SELECT; an array; a quoted identifier. Query fragments nest.                                                                                                                                           | `denext.14`  |
| `sql.unsafe(text, params)`, `sql.file(path, params)`, `sql.array(values, type)` | Raw text with parameters; a query read from a file (read permission); a typed array parameter (`$n::type[]`).                                                                                                                                                                         | `denext.14`  |
| `sql.begin([options,] fn)`, `tx.savepoint(fn)`                                  | A transaction (ROLLBACK when `fn` throws) and nested savepoints. BEGIN and COMMIT are pipelined with the statements when they can be.                                                                                                                                                 | `denext.14`  |
| `sql.reserve()`, `sql.close({ timeout })`, `sql.end()`                          | A dedicated connection; shut the pool down.                                                                                                                                                                                                                                           | `denext.14`  |
| `sql.listen(channel, fn, onlisten?)`, `sql.notify(channel, payload)`            | Postgres LISTEN / NOTIFY on one dedicated connection that reconnects with backoff.                                                                                                                                                                                                    | `denext.14`  |
| `result.columns`                                                                | One object per result column (`name`, `type`, `nullable`, `table`, `column`; Postgres adds `typeOid`, `typeKind`, `baseType`, …; SQLite `database`), on every result shape, empty ones included.                                                                                      | `3.0.0-rc.1` |
| `Deno.SQL.PostgresError`, `Deno.SQL.SQLiteError`                                | Error classes. A Postgres server error: `code` is the SQLSTATE (also `errno`), plus `detail`, `hint`, `position`, `constraint`, …; client failures carry `ERR_POSTGRES_*` codes.                                                                                                      | `denext.14`  |

Values: `int2` / `int4` / floats as numbers, `int8` and `numeric` as strings (`bigint: true`:
`bigint`), `json` / `jsonb` parsed, `bytea` as `Uint8Array`, `timestamptz` / `date` as `Date`,
`timestamp` as local wall-clock time, arrays, enums, ranges and geometry as objects. Postgres runs
over the runtime's own TLS stack (`sslmode` `disable` to `verify-full`, client certificates,
Unix-socket hosts); `--allow-net` is checked for the host and for each address it resolves to.
SQLite needs read (and, unless read-only, write) permission for the file. Not yet: MySQL.

### `Deno.serve` and HTTP

| API                                 | What                                                                                                                                                                                                                                                             | Example                                          | Since        |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------ |
| `request.signal` (default behavior) | Aborts only when the client disconnects or the request times out, never after a delivered response. Use `info.completed` to learn a response was delivered. Opt back in with `--unstable-legacy-abort`, `"unstable": ["legacy-abort"]` or `DENO_LEGACY_ABORT=1`. | `fetch(upstream, { signal: req.signal })`        | `3.0.0-rc.5` |
| `DENO_SERVE_ADDRESS=memory:<name>`  | Serves `Deno.serve` (and `node:http`) on an in-process memory transport: no socket and no net permission. The Deno Desktop runtime serves an app's origin this way; a TCP server refuses a request target that claims `http+memory:`.                            | `DENO_SERVE_ADDRESS=memory:app deno run main.ts` | `denext.1`   |
| `--unstable-idle-trim`              | Once the event loop has been idle 1 s after activity, a full GC and `malloc_trim(0)` return a server's memory to the OS. glibc Linux only (accepted and inert elsewhere). Also `"unstable": ["idle-trim"]` or `DENO_UNSTABLE_IDLE_TRIM=1`; tuning below.         | `deno run --unstable-idle-trim -A server.ts`     | `3.0.0-rc.5` |

`denext start` turns the idle trim on for you; see
[Deployment targets › Idle memory trim](/docs/deployment-targets#idle-memory-trim).

## `deno test`: Vitest and Jest

Vitest and Jest suites run unchanged under `deno test`: `vitest`, `vitest/config`,
`vite-plus/test` and `@jest/globals` resolve to built-in modules (Vitest's own runtime, vendored).
A `vitest.config.*`, a `vite.config.*` of a Vitest project, a `jest.config.*` or a package.json
`jest` key is read for `include` / `exclude`, `projects`, `setupFiles`, `globals`, `environment`
(the project's jsdom or happy-dom), aliases and tsconfig paths, `define` / `.env`, and Jest's
`moduleNameMapper`, `testEnvironment`, `fakeTimers` and the rest. Module mocking (`vi.mock`,
`vi.hoisted`, `vi.importActual`, `vi.spyOn(namespace, "export")`, `jest.mock`), snapshots and fake
timers work as in Vitest and Jest. Each test is a `Deno.test`, so `--filter`, the reporters and
the summary see one test per Vitest test. Since `denext.14`. `denext test` runs your
`*.vitest.ts` files this way ([Toolchain](/docs/toolchain#denext-task-deno-task-and-tests)).

| Behavior                              | What                                                                                                                                                                                                                               | Since        |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| Permissions                           | A Vitest file needs only the permissions its own code does: the runner reads its config, setup files and `__mocks__` without `--allow-read`, inside the run's root.                                                                | `denext.14`  |
| No `Deno` in a Vitest or Jest project | User modules see `typeof Deno === "undefined"`, as under Node.js; `globalThis.Deno` still reaches it.                                                                                                                              | `denext.14`  |
| Coverage across plain and Vitest runs | `deno coverage` merges a module run by plain `Deno.test` files and by Vitest files line for line.                                                                                                                                  | `denext.17`  |
| Coverage on SIGINT / SIGTERM          | `deno run --coverage` (or `DENO_COVERAGE_DIR`, `--cpu-prof`) and `deno test --coverage` still write their data when a signal ends them, unless the program handles the signal itself. Not on Windows SIGTERM, not under `--watch`. | `3.0.0-rc.6` |

## Node.js and npm projects

A project with a `package.json` and no `deno.json` (an app brought over from Node.js) resolves and
installs as Node.js and npm do. A native denext app has a `deno.json` and keeps Deno's resolution.
See [npm packages as on Node.js](/docs/toolchain#npm-packages-as-on-nodejs).

| Behavior                                   | What                                                                                                                                                                                       | Opt out                                                                        | Since       |

## npm supply chain

Four gates on what `deno install` and `deno add` let in. The `.npmrc` keys also read
`npm_config_<key>` from the environment; deno.json's `supplyChain` (the workspace root's only)
mirrors them. Where sources disagree the stricter value wins.

| `.npmrc` key                 | deno.json `supplyChain`                                                         | Default                    | What                                                                                                                                   | Since        |
| ---------------------------- | ------------------------------------------------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `jail-scripts`               | `jailScripts`: `true` / `false` / `{ net, packages, upstreamByName }`           | `true` (from `3.0.0-rc.5`) | An approved dependency's lifecycle script runs jailed: scrubbed environment, scratch HOME, limited writes, no network, OS confinement. | `3.0.0-rc.2` |
|                              | `jailScripts.packages.<name>`: `{ env, write, net, executables, allowPrivate }` |                            | One package's exceptions. `net`: `true`, `false` or a host list (`3.0.0-rc.6`); `write` paths may start with `~` (`3.0.0-rc.6`).       | `3.0.0-rc.2` |
| `advisory-check`             | `advisoryCheck`: `"on"` / `"off"` / `"required"`                                | `on`                       | Refuses a version OSV lists as malicious (`MAL-…`); `required` also refuses when OSV can't be reached.                                 | `3.0.0-rc.2` |
| `low-download-check`         | `lowDownloadCheck`: `"off"` / `"warn"` / `"prompt"` / `"required"`              | `warn`                     | What `deno add` does for a new package with few weekly downloads (a typosquat guard).                                                  | `3.0.0-rc.2` |
| `low-download-threshold`     | `lowDownloadThreshold`                                                          | `1000`                     | Weekly downloads below which that check applies; `0` turns it off.                                                                     | `3.0.0-rc.2` |
| `allowed-unpopular-packages` | `allowLowDownloads`                                                             |                            | Names (or `@scope/*`, `prefix*`) added whatever their counts.                                                                          | `3.0.0-rc.2` |
| `paranoid`                   | `paranoid`                                                                      | `false`                    | Every gate on and failing closed; a weaker setting anywhere is an error.                                                               | `3.0.0-rc.2` |

The jail, its exceptions and what denext writes for you are in
[Supply chain: lifecycle-script jail](/docs/toolchain#supply-chain-lifecycle-script-jail); the
other three gates in [Supply chain: install gates](/docs/toolchain#supply-chain-install-gates).

## Deno Desktop APIs

The Deno Desktop runtime is the `libdenort` library `deno desktop` embeds an app into, built from
the same fork with [laufey](https://github.com/Brainwires/laufey)'s window hosts. These APIs exist
only inside a packaged or `denext desktop dev` app; in a plain `deno run` they answer "not
supported". In a denext app you normally reach them through `denext/mobile`, `denext/desktop/window`,
`denext/desktop/app` and `denext/desktop/client` ([Desktop apps](/docs/desktop)), which also work
on the web and in the mobile shell. Each row links to its section of
[Our Deno Desktop runtime](/docs/desktop-runtime), which says why it exists and how it is tested.
Stock Deno Desktop 2.9.8 has none of these.

## What isn't here

- **Internal fixes.** Crash and hang fixes, the security pull requests carried ahead of upstream,
  Windows process-handle fixes and dependency updates change no API. They are listed in the fork's
  DENEXT.md and summarised per release under [Tracking Deno](/docs/toolchain#tracking-deno).
- **Not yet in the runtime:** MySQL in `Deno.SQL`; type-aware lint in `deno lsp`; `module.register()`
  hooks for `require()` (as in Node); an OS auth session on Windows and Linux (they have none).
