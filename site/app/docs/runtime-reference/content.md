denext runs your project on its own build of Deno: the CLI, `denort` (what `deno compile` and
`denext build --compile` build onto) and the Deno Desktop runtime, all from the public
[Brainwires/deno](https://github.com/Brainwires/deno) fork. It is stock Deno 2.9.8 plus the
additions below. You don't install it: denext downloads the build it pins, checks its SHA-256 and
runs every command that needs Deno on it ([denext's Deno toolchain](/docs/toolchain)).

This page lists what the fork adds that you can see or use. Internal fixes (crash fixes, security
patches carried ahead of upstream, test and CI changes) are described in the fork's
[DENEXT.md](https://github.com/Brainwires/deno/blob/development-denext/DENEXT.md). The tables
give each runtime version in full (`2.9.7-denext.15`, `3.0.0-rc.6`, `3.0.0-denext.21`).

## Which runtime am I on?

From runtime `3.0.0-rc.3` the runtime says whose it is, so code needn't infer it from the version
number (there is no upstream Deno 3.0; denext checks the marker too):

```ts
if (Deno.build.denext) {
  console.log(`denext's Deno ${Deno.build.denext}`); // "3.0.0-denext.21"
} else {
  console.log("stock Deno: Deno.SQL and the other additions are not here");
}
```

```text
$ deno --version
deno 3.0.0-denext.21 (stable, release, aarch64-apple-darwin)
v8 15.6.75.57-rusty
typescript 6.0.3
denext 3.0.0-denext.21 (Brainwires)
```

| What                       | Detail                                                                                                                                                                                            | Since        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `Deno.build.denext`        | The runtime's version, a string, in the main thread and in workers. `undefined` on stock Deno.                                                                                                    | `3.0.0-rc.3` |
| `deno --version` last line | `denext <version> (Brainwires)`; `deno -V` stays one line.                                                                                                                                        | `3.0.0-rc.3` |
| `Deno.version.deno`        | The fork's own version (`3.0.0-denext.21`), also in the user agent (`Deno/3.0.0-denext.21`). Before `3.0.0-rc.1` it was `2.9.7-denext.N`.                                                         | `3.0.0-rc.1` |
| `deno upgrade`             | Refuses to run in a release build, and the background update check is off: upstream's channels would replace the fork with stock Deno. Use `denext upgrade` or `denext toolchain install`.        | `3.0.0-rc.1` |
| Release channel            | `deno --version` says `stable`, the channel of the Deno release the build is made from (2.9.8). `npm` `engines.deno` ranges are checked against that release, not against the prerelease version. | `3.0.0-rc.1` |

The versions sort in release order: `2.9.7-denext.1` … `2.9.7-denext.22`, then `3.0.0-rc.1` …
`3.0.0-rc.6`, then `3.0.0-denext.1`, `3.0.0-denext.2`, … (there is no `3.0.0-denext.4`, `3.0.0-denext.9`, `3.0.0-denext.11`, `3.0.0-denext.14` or `3.0.0-denext.15` release, nor any between `3.0.0-denext.18` and `3.0.0-denext.21`). That is semver's order with one
exception: denext ranks the `3.0.0-denext.N` releases above every `3.0.0-rc.N`, where plain semver
would put them below. There is no upstream 3.0: upstream Deno stays on its 2.9.x LTS line, and
denext's runtime is the forward line. Every "Since" cell below names the full release: a
`2.9.7-denext.N` row comes from the first line (`2.9.7-denext.1` to `2.9.7-denext.22`), which sorts
before every `3.0.0` release, so `2.9.7-denext.16` is not `3.0.0-denext.16`. `3.0.0-denext.14` and
`3.0.0-denext.15` were never released; their work shipped in `3.0.0-denext.16`. No release between `3.0.0-denext.18` and
`3.0.0-denext.21` was published; that work shipped in `3.0.0-denext.21`.
Every row below applies to the runtime denext pins (`denext toolchain status` names it); a later
release's rows are added once denext pins it. Before the marker (`3.0.0-rc.2` and earlier) denext recognises its runtime by the version alone ([Versions](/docs/toolchain#versions)).

**Required from denext 5.0 (planned).** Today every denext command still has the stock-Deno
escape hatch, `DENEXT_DENO=stock`, and what needs the fork falls back or says why it can't. From
denext 5.0 the plan is to require denext's runtime: the stock-Deno fallbacks go away, and features
such as `Deno.SQL`, the jail and native TypeScript 7 stop being optional. Until 5.0 ships, nothing
changes for a project on stock Deno.

## JavaScript and TypeScript APIs

### `Deno.SQL` and `Deno.sql`

A built-in SQL client for Postgres and SQLite with Bun's `Bun.sql` surface and no npm. Every
interpolated value is sent as a parameter, never spliced into the text. Since `2.9.7-denext.15`, the first release with the fork's own CLI archive; stock Deno has none
(its nearest is `npm:postgres`). The Postgres side of [Database](/docs/database#postgres) and
`postgresClient()` run on it.

```ts
const sql = new Deno.SQL(Deno.env.get("DATABASE_URL")!, { max: 10 });
const users = await sql`select id, name from users where id = ${id}`;
await sql`insert into users ${sql({ name: "Ada" })}`;
await sql.begin(async (tx) => {
  await tx`update accounts set balance = balance - ${n} where id = ${from}`;
  await tx`update accounts set balance = balance + ${n} where id = ${to}`;
});
```

Values: `int2` / `int4` / floats as numbers, `int8` and `numeric` as strings (`bigint: true`:
`bigint`), `json` / `jsonb` parsed, `bytea` as `Uint8Array`, `timestamptz` / `date` as `Date`,
`timestamp` as local wall-clock time, arrays, enums, ranges and geometry as objects. Postgres runs
over the runtime's own TLS stack (`sslmode` `disable` to `verify-full`, client certificates,
Unix-socket hosts); `--allow-net` is checked for the host and for each address it resolves to.
SQLite needs read (and, unless read-only, write) permission for the file. Not yet: MySQL.

## Permissions and network behavior

Deno's permissions are least-privilege guardrails: checks inside Deno's own APIs, not an OS
sandbox. A subprocess, FFI or a native addon goes around them, and kernel enforcement (Landlock,
Seatbelt) is planned, not shipped. The grants that amount to full trust, symlinks and allow scopes,
and how network rules behave with a proxy are on [Permissions](/docs/permissions).

## Deno Desktop APIs

The Deno Desktop runtime is the `libdenort` library `deno desktop` embeds an app into, built from
the same fork with [laufey](https://github.com/Brainwires/laufey)'s window hosts. These APIs exist
only inside a packaged or `denext desktop dev` app; in a plain `deno run` they answer "not
supported". In a denext app you normally reach them through `denext/mobile`, `denext/desktop/window`,
`denext/desktop/app` and `denext/desktop/client` ([Desktop apps](/docs/desktop)), which also work
on the web and in the mobile shell. Each row links to its section of
[Our Deno Desktop runtime](/docs/desktop-runtime), which says why it exists and how it is tested.
Stock Deno Desktop 2.9.8 has none of these.

## What isn't here

- **Internal fixes.** Crash and hang fixes, the security pull requests carried ahead of upstream,
  Windows process-handle fixes and dependency updates change no API. They are listed in the fork's
  DENEXT.md and summarised per release under [Tracking Deno](/docs/toolchain#tracking-deno).
- **Not yet in the runtime:** MySQL in `Deno.SQL`; type-aware lint in `deno lsp`; `module.register()`
  hooks for `require()` (as in Node); an OS auth session on Windows and Linux (they have none).
