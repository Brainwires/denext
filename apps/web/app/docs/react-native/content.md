denext can build a React Native / Expo app for the browser as a [SPA](/docs/spa):
`react-native` resolves to [react-native-web](https://necolas.github.io/react-native-web/),
the components render to the DOM, and denext's React runs them. Rendering stays DOM; this is
API compatibility, not native rendering.

It was measured on T3 Code's Expo app: with `reactNative: true` in place of hand patches to
the bundler, every deep-linked route renders the same text as before. The `expo-*` packages the
app uses resolve to denext's [Expo API shims](#expo-apis), so the web-only code left is the
app's own stubs for native-only modules and its Tailwind wiring.

## Setup

Install `react-native-web` next to the app's other dependencies (`npm install react-native-web`,
or your workspace's package manager), then turn the mode on:

```ts
// denext.config.ts
import type { DenextConfig } from "denext/server";

export default {
  mode: "spa",
  reactNative: true,
  spa: { entry: "./index.ts", title: "My app" },
} satisfies DenextConfig;
```

The project needs a `deno.json` like any compat SPA: `react`, `react-dom` and the JSX runtimes
aliased to denext, and `"nodeModulesDir": "manual"` so the app's npm packages are read from its
`node_modules`. [`denext migrate --from expo`](#migrating-an-expo-app) writes it, the config
above and a Capacitor shell config for you. `react-native` itself needs no entry: the resolve
mode claims it.

## Migrating an Expo app

```sh
denext migrate --from expo   # auto-detected when `expo` is a dependency
```

It writes three files and changes no source:

- **`deno.json`**: the React family aliased to denext, `nodeModulesDir` as for a Vite SPA
  (`"manual"` when a lockfile says the app installs its own `node_modules`), the `dev` /
  `build` / `export` / `start` tasks, and `mobile:sync` / `mobile:ios` / `mobile:android`.
- **`denext.config.ts`**: `mode: "spa"`, `reactNative: true`, `spa.entry` = the app's own
  entry (package.json `main`; for Expo's default entry, a generated `index.web.ts` that mounts
  `./App`; for expo-router, a generated `index.web.ts` with its web entry minus Metro's
  runtime), `spa.head` setting [`__DENEXT_EXPO_CONFIG__`](#expo-apis) from the app config, and
  `spa.precompress: false` (the Capacitor shell loads files as they are).
- **`capacitor.config.ts`**: `appId` from `ios.bundleIdentifier` (else `android.package`),
  `appName` from `name`, `webDir: "out"`.

The app config (`app.json`, `app.config.ts` / `.js`) is **read statically; migrate never runs
project code**. Literal values, top-level `const`s, member access on them and template literals
are followed; a value computed in code (`process.env`, a function call, a variant picked at run
time) is listed as not statically readable, and `app.json`'s value is used when it has one. A
placeholder `appId` is marked `TODO` in `capacitor.config.ts`.

The report then lists:

- each `expo-*` dependency with its [shim](#expo-apis) status and how many exports it omits, or
  "no shim" (it resolves to the real package, which needs a web build);
- **native-only packages**: Nitro modules, TurboModule / Fabric codegen packages, Expo native
  modules without a web platform, and packages whose modules exist only as `.ios` / `.android`
  files. Their native parts do not exist in a WebView: some load and do nothing, others throw
  when used. Give each [a web replacement](#other-native-only-packages);
- modules only the app's Metro config provides (`resolver.extraNodeModules` names no installed
  package supplies) and a custom `resolveRequest`: map each in `deno.json` `imports`;
- packages the web build still needs (`react-native-web`, and `@sqlite.org/sqlite-wasm` for
  `expo-sqlite`);
- the `denext mobile add …` command for the Capacitor shell, derived from the `expo-*` packages,
  config plugins, iOS usage strings, Android permissions, `scheme` (`--scheme`) and
  `ios.associatedDomains` (`--domain`); and the usage strings and permissions to copy by hand;
- a Tailwind input (`global.css`) for uniwind / NativeWind, which needs [the recipe](#recipe-uniwind-and-tailwind).

On T3 Code's `apps/mobile`, the migrated app's build failed on exactly the three modules the
report named (two generated by its Metro config, and `react-native-image-viewing`'s
iOS/Android-only files). With the app's own stubs for those and for the flagged native modules
it builds, and all 41 swept routes render clean.

## The web entry

The app's own entry works as the SPA entry: `registerRootComponent` from `expo` resolves to
[`denext/expo/expo`](#expo-apis), which mounts the root component on the SPA's `#root` through
react-native-web's `AppRegistry`, as Expo's web build does:

```ts
// index.ts (unchanged)
import { registerRootComponent } from "expo";
import App from "./src/App";

registerRootComponent(App);
```

An app that does not use `expo` (or turns the shims off) registers the root itself:

```tsx
// web-entry.tsx
import { AppRegistry } from "react-native";
import App from "./src/App";

AppRegistry.registerComponent("main", () => App);
AppRegistry.runApplication("main", { rootTag: document.getElementById("root") });
```

Import anything the native entry imports first for its side effects, such as
`react-native-gesture-handler`, at the top of that file as well.

### expo-router

expo-router works in React Native mode. Its web build finds the routes with Metro's
`require.context` over the route directory (`expo-router/_ctx`); React Native mode resolves
that module to a context generated at build time from `app/` (or `src/app/`), the files
expo-router's own pattern admits (not `+api`, `+middleware`, `+html`, `+native-intent`, or the
`.ios` / `.android` / `.native` variants). Each build, and each rebuild of the dev loop, scans
the directory again. The entry is expo-router's own, without `@expo/metro-runtime` (Metro's
runtime); `denext migrate --from expo` writes it:

```ts
// index.web.ts
import { App } from "expo-router/build/qualified-entry";
import { renderRootComponent } from "expo-router/build/renderRootComponent";

renderRootComponent(App);
```

Measured on a fresh expo-router 57 app: `/`, `/about`, the unmatched-route page and `<Link>`
navigation all render with no console errors.

## What `reactNative` does

| Piece                  | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `react-native` imports | `react-native` and every `react-native/…` subpath resolve to the installed react-native-web, for every importer, even when a real `react-native` is installed (its Flow source is never reached). The package is resolved to its real path, so pnpm works.                                                                                                                                                                                                  |
| Deep `Libraries/…`     | `react-native/Libraries/<path>` maps to react-native-web's vendored copy of the same path, then its export or internal module of the same name (`Libraries/Components/View/View` → `View`, `Libraries/Image/AssetRegistry` → `AssetRegistry`).                                                                                                                                                                                                              |
| Native-only internals  | A deep import with no web equivalent (the Fabric renderer shims, native module specs) loads a stub. Importing it is harmless; calling or constructing any export throws an error that names the import.                                                                                                                                                                                                                                                     |
| Codegen entry points   | `TurboModuleRegistry`, `codegenNativeComponent` and `codegenNativeCommands` import from `react-native` and from their `Libraries/…` paths. No native module exists on the web: `get(name)` returns `null`, and `getEnforcing(name)` returns a stand-in that loads harmlessly and throws an error naming the module when a method or property is used. A codegen component renders nothing (with a dev warning, once per name), and its commands do nothing. |
| Platform files         | `.web.tsx`, `.web.ts`, `.web.jsx` and `.web.js` are tried before the plain extensions, for relative and alias imports and for package subpaths, so `Button.web.tsx` wins over `Button.tsx` and a library's web build wins over its native spec files.                                                                                                                                                                                                       |
| JSX in `.js`           | `.js` files are parsed as JSX. React Native libraries ship JSX in `.js`, which Metro's Babel preset accepts.                                                                                                                                                                                                                                                                                                                                                |
| Build-time globals     | `__DEV__` (true in `denext dev`, false in a production build), `global` → `globalThis`, and `process.env.EXPO_OS` → `"web"`.                                                                                                                                                                                                                                                                                                                                |
| `Appearance`           | react-native-web's `Appearance` gains `setColorScheme` (React Native 0.72+): `"light"` / `"dark"` override the system scheme for `getColorScheme()`, the change listeners (so `useColorScheme()`) and the root element's `color-scheme`; `"unspecified"` or `null` restores it. No hand polyfill is needed.                                                                                                                                                 |
| expo-router            | `expo-router/_ctx` resolves to a route context generated from `app/` ([expo-router](#expo-router)).                                                                                                                                                                                                                                                                                                                                                         |
| `expo-*` packages      | Each package with a [denext shim](#expo-apis) (`expo-haptics`, `expo-secure-store`, …, and `expo` with `expo/fetch`) resolves to `denext/expo/<name>`, from the same denext instance as the app. A package without a shim, or a subpath the shim does not cover, resolves normally.                                                                                                                                                                         |
| Root style             | The SPA shell gets Expo web's root style, `html,body,#root{height:100%;margin:0}` and `#root{display:flex}`, ahead of `spa.head`. React Native's root view is `flex: 1` and needs a sized flex parent; without it, overlays cover the page and take the taps.                                                                                                                                                                                               |

The mode always builds through the esbuild (compat) pipeline, and it applies to `denext build`,
`denext export` and `denext dev`. In dev a React Native app uses the bundled loop (a rebuild and
reload per change) rather than the per-module one, because the resolution above lives in the
bundler; an explicit `unbundled: true` dev server option is refused with that reason. Package subpath probing needs the default `nodeResolve`.

`reactNative` is valid only with `mode: "spa"`; anywhere else the config fails validation.

### Options

Pass an object instead of `true` to change a default:

```ts
reactNative: {
  // Leave the root style out (you set your own in spa.head or your CSS).
  rootStyle: false,
  // Resolve every expo-* package normally instead of to denext's shims.
  expoShims: false,
},
```

## Images

`require("./logo.png")` and `import logo from "./logo.png"` resolve to the emitted file's URL,
which react-native-web's `<Image source={…}>` accepts. Resolution-variant files (`logo@2x.png`,
`logo@3x.png`) are not picked by pixel ratio as Metro does: the file you name is the file you
get. Name the variant you want, or keep a plain `logo.png` next to the variants.

## Expo APIs

same API, implemented over [`denext/mobile`](/docs/desktop) (a Capacitor plugin inside the
native shell, a web API in the browser) or directly over web APIs. App code keeps its
`import * as Haptics from "expo-haptics"`. The versions are the ones each shim's API was
matched against (Expo SDK 57); `full` is the whole API, `partial` the commonly used part with
the differences noted, and `stub` a native-only or config-only package that loads and does

The list is `EXPO_SHIMS` in `denext/expo/manifest`. A few things to know:

- **Synchronous APIs.** Some Expo APIs are synchronous because they run over JSI. The
  Capacitor bridge is asynchronous, so `expo-secure-store`'s `getItem` / `setItem` are not
  provided (use the `…Async` forms), and `expo-file-system`'s sync calls act on an index the
  shim keeps and reach the files in the background (see its row).
- **The app config.** `expo-constants`' `expoConfig` (and `expo-updates`' server URL, and
  `expo-linking`'s scheme) come from `globalThis.__DENEXT_EXPO_CONFIG__`: set it to the
  `expo` object of your app config before the bundle runs, for example in `spa.head`:
  `<script>globalThis.__DENEXT_EXPO_CONFIG__ = {"name":"My app","scheme":"myapp"}</script>`.
- **Capabilities.** Inside the Capacitor shell each backed call needs its plugin installed:
  `denext mobile add <capability>` (haptics, clipboard, share, secure-store, push, …).
- **`expo-sqlite`** runs natively through `@capacitor-community/sqlite` (`denext mobile add
  sqlite`). On the web it needs the official engine installed in the app: `npm install
  @sqlite.org/sqlite-wasm` (denext ships no npm runtime dependency; without it, opening a
  database fails with an error naming the package). The build emits the engine's module and
  `sqlite3.wasm` as assets, and the database runs in a worker on the engine's `opfs-sahpool`
  VFS: persisted to the Origin Private File System, with no COOP/COEP headers needed (Expo's own
  web build uses the engine's `"opfs"` VFS, which needs a cross-origin-isolated page and
  otherwise never opens the database). Where OPFS is unavailable, or another tab of the origin
  holds the pool, the database is in memory for the session. The same functions are
  `openSqlite` / `deleteSqlite` in [`denext/mobile`](/docs/desktop).

## Other native-only packages

Packages with no web build and no denext shim (native modules, Nitro/JSI packages) still need
a web replacement of your own. A TurboModule / Fabric codegen package loads as it is, because of the
[codegen entry points](#the-web-entry): its spec's top-level `getEnforcing` no longer throws,
so the package fails only when its native module is actually used. It still needs a
replacement if the web build calls into that module. Two ways:

- Add a `.web.ts` beside the module that imports it, exporting a web implementation. The
  platform-file rule picks it up.
- Map the package to a shim in `deno.json`'s `imports`, for example
  `"react-native-nitro-markdown": "./web-shims/nitro-markdown.ts"`.

## Recipe: uniwind and Tailwind

uniwind styles React Native components with Tailwind classes. Its web
setup is specific to the app, so denext does not build it in. What it takes:

1. Compile the Tailwind input with denext's Tailwind integration:
   `tailwind: { input: "./global.css", output: "./global.gen.css" }` in `denext.config.ts`,
   and import `global.css` from the web entry.
2. Run `uniwind generate-artifacts` once for any themes beyond the default, and commit the
   generated CSS it writes.
3. Two importer-sensitive aliases: `react-native` imported from anywhere except uniwind's own
   files resolves to uniwind's web components (`uniwind/dist/module/components/web/index.js`),
   and react-native-web's `StyleSheet` importing `./createOrderedCSSStyleSheet` gets uniwind's
   version from the same directory.

denext's config has no seam for importer-sensitive aliases yet. Until it has one, apply step 3
with [`denext patch`](/docs/patches): patch `src/build/react-native.ts` so the `react-native`
resolver returns uniwind's index when the importer is outside `/uniwind/dist/`, and
`src/build/next-compat.ts`'s app resolver so the `./createOrderedCSSStyleSheet` import from
`react-native-web/dist/exports/StyleSheet` returns uniwind's file.
