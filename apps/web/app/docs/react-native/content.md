denext can build a React Native / Expo app for the browser as a [SPA](/docs/spa):
`react-native` resolves to [react-native-web](https://necolas.github.io/react-native-web/),
the components render to the DOM, and denext's React runs them. Rendering stays DOM; this is
API compatibility, not native rendering.

It was measured on T3 Code's Expo app: with `reactNative: true` in place of hand patches to
the bundler, every deep-linked route renders the same text as before. The `expo-*` packages the
app uses resolve to denext's [Expo API shims](#expo-apis), so the web-only code left is the
app's own stubs for native-only modules and its Tailwind wiring.

Deciding whether to move an app at all? [denext vs React Native](/docs/vs-react-native) sets
the measurements against the WebView's inherent limits.

## Setup

Install `react-native-web` next to the app's other dependencies (`npm install react-native-web`,
or your workspace's package manager), then turn the mode on:

```ts
// denext.config.ts
import type { DenextConfig } from "denext/server";

export default {
  mode: "spa",
  reactNative: true,
  spa: { entry: "./index.ts", title: "My app" },
} satisfies DenextConfig;
```

The project needs a `deno.json` like any compat SPA: `react`, `react-dom` and the JSX runtimes
aliased to denext, and `"nodeModulesDir": "manual"` so the app's npm packages are read from its
`node_modules`. [`denext migrate --from expo`](#migrating-an-expo-app) writes it, the config
above and a Capacitor shell config for you. `react-native` itself needs no entry: the resolve
mode claims it.

## Migrating an Expo app

```sh
denext migrate --from expo   # auto-detected when `expo` is a dependency
```

It writes three files and changes no source:

- **`deno.json`**: the React family aliased to denext, `nodeModulesDir` as for a Vite SPA
  (`"manual"` when a lockfile says the app installs its own `node_modules`), the `dev` /
  `build` / `export` / `start` tasks, and `mobile:sync` / `mobile:ios` / `mobile:android`.
- **`denext.config.ts`**: `mode: "spa"`, `reactNative: true`, `spa.entry` = the app's own
  entry (package.json `main`; for Expo's default entry, a generated `index.web.ts` that mounts
  `./App`; for expo-router, a generated `index.web.ts` with its web entry minus Metro's
  runtime), `spa.head` setting [`__DENEXT_EXPO_CONFIG__`](#expo-apis) from the app config, and
  `spa.precompress: false` (the Capacitor shell loads files as they are).
- **`capacitor.config.ts`**: `appId` from `ios.bundleIdentifier` (else `android.package`),
  `appName` from `name`, `webDir: "out"`.

When the app depends on `react-native-macos` or `react-native-windows`, the config gets
`reactNative: { desktopPackage: "<that package>" }` ([Options](#options)); with both, it keeps
`reactNative: true` and leaves the two choices commented.

The app config (`app.json`, `app.config.ts` / `.js`) is **read statically; migrate never runs
project code**. Literal values, top-level `const`s, member access on them and template literals
are followed; a value computed in code (`process.env`, a function call, a variant picked at run
time) is listed as not statically readable, and `app.json`'s value is used when it has one. A
placeholder `appId` is marked `TODO` in `capacitor.config.ts`.

The report then lists:

- each `expo-*` dependency with its [shim](#expo-apis) status and how many exports it omits, or
  "no shim" (it resolves to the real package, which needs a web build);
- **native-only packages**: Nitro modules, TurboModule / Fabric codegen packages, Expo native
  modules without a web platform, and packages whose modules exist only as `.ios` / `.android`
  files. Their native parts do not exist in a WebView: some load and do nothing, others throw
  when used. Give each [a web replacement](#other-native-only-packages);
- modules only the app's Metro config provides (`resolver.extraNodeModules` names no installed
  package supplies) and a custom `resolveRequest`: map each in `deno.json` `imports`;
- packages the web build still needs (`react-native-web`, and `@sqlite.org/sqlite-wasm` for
  `expo-sqlite`);
- the `denext mobile add …` command for the Capacitor shell, derived from the `expo-*` packages,
  config plugins, iOS usage strings, Android permissions, `scheme` (`--scheme`) and
  `ios.associatedDomains` (`--domain`); and the usage strings and permissions to copy by hand;
- a Tailwind input (`global.css`) for uniwind / NativeWind, which needs [the recipe](#recipe-uniwind-and-tailwind).

On T3 Code's `apps/mobile`, the migrated app's build failed on exactly the three modules the
report named (two generated by its Metro config, and `react-native-image-viewing`'s
iOS/Android-only files). With the app's own stubs for those and for the flagged native modules
it builds, and all 41 swept routes render clean.

## The web entry

The app's own entry works as the SPA entry: `registerRootComponent` from `expo` resolves to
[`denext/expo/expo`](#expo-apis), which mounts the root component on the SPA's `#root` through
react-native-web's `AppRegistry`, as Expo's web build does:

```ts
// index.ts (unchanged)
import { registerRootComponent } from "expo";
import App from "./src/App";

registerRootComponent(App);
```

An app that does not use `expo` (or turns the shims off) registers the root itself:

```tsx
// web-entry.tsx
import { AppRegistry } from "react-native";
import App from "./src/App";

AppRegistry.registerComponent("main", () => App);
AppRegistry.runApplication("main", { rootTag: document.getElementById("root") });
```

Import anything the native entry imports first for its side effects, such as
`react-native-gesture-handler`, at the top of that file as well.

### expo-router

expo-router works in React Native mode. Its web build finds the routes with Metro's
`require.context` over the route directory (`expo-router/_ctx`); React Native mode resolves
that module to a context generated at build time from `app/` (or `src/app/`), the files
expo-router's own pattern admits (not `+api`, `+middleware`, `+html`, `+native-intent`, or the
`.ios` / `.android` / `.native` variants). Each build, and each rebuild of the dev loop, scans
the directory again. The entry is expo-router's own, without `@expo/metro-runtime` (Metro's
runtime); `denext migrate --from expo` writes it:

```ts
// index.web.ts
import { App } from "expo-router/build/qualified-entry";
import { renderRootComponent } from "expo-router/build/renderRootComponent";

renderRootComponent(App);
```

Measured on a fresh expo-router 57 app: `/`, `/about`, the unmatched-route page and `<Link>`
navigation all render with no console errors, and a real-browser test builds an expo-router
57 app and checks its `Stack` and `Tabs`.

expo-router's `Stack` and `Tabs` (from `expo-router`, `expo-router/stack` and
`expo-router/tabs`) are replaced at build time with navigators drawn by
[`denext/navigation`](/docs/navigation-native): kept screens, platform push and pop animations,
the iOS swipe back, Android predictive back, a native-style header, and `modal` / `formSheet`
/ `transparentModal` presentations. Routes, `router.push`, `<Link>` and `Stack.Screen` options
behave as before; the details are in
[Native-feel navigation](/docs/navigation-native#react-native-mode).

`denext export` and `denext dev`. Package subpath probing needs the default `nodeResolve`.

### Fast Refresh

`denext dev` serves a React Native app on the per-module loop, as it does any SPA. An edit to a
component module (`.tsx`, `.jsx`, or `.js`, which holds JSX in this mode) re-transforms that one
module and swaps it into the running page with its hook state kept: no rebuild, no reload. The
app's own modules are served one by one, with `.web.*` probed first, `.js` parsed as JSX, the
globals above defined, the worklets transform applied and a static `require("./icon.png")`
turned into an import. Every package the app imports (and every image or font it imports) is
served from one dependency bundle, built once through the resolution above, the way
`denext build` resolves it; React and denext stay outside it, so the page has one instance of
each.

The page reloads (state is lost) when:

- the app imports a package for the first time, or a name it has not imported from that package
  before: the dependency bundle is rebuilt, and the page reloads onto it;
- an expo-router route file is added or removed (the route context is part of the bundle);
- `package.json` or a lockfile changes;
- the edited module is not a component (a `.ts` helper), the SPA entry or a `public/` file, as
  in any SPA.

It works the same on a device: [`denext mobile dev --lan`](/docs/mobile#live-reload-on-a-device)
points the Capacitor shell at the dev server, and an edit updates the running app in place.
`DENEXT_DEV_UNBUNDLED=0` (or the `unbundled: false` dev server option) returns to the bundled
loop, which rebuilds the whole app on each change.

`reactNative` is valid only with `mode: "spa"`; anywhere else the config fails validation.

### Options

Pass an object instead of `true` to change a default:

```ts
reactNative: {
  // Leave the root style and the viewport-fit=cover default out (you set your own in
  // spa.head or your CSS).
  rootStyle: false,
  // Resolve every expo-* package normally instead of to denext's shims.
  expoShims: false,
  // Keep react-native-web's FlatList / SectionList / VirtualizedList, FlashList and
  // LegendList engines instead of denext's VirtualList (default: "denext").
  lists: "library",
  // Resolve one community package to the real library again (see Community packages).
  aliases: { "react-native-webview": false },
  // Build the app's own `react-native` imports as a desktop package, as Metro does for a
  // macOS / Windows build (see React Native on desktop). node_modules keep react-native.
  desktopPackage: "react-native-macos",
},
```

## React Native APIs

react-native-web ships several React Native APIs as mocks ("no equivalent web APIs"), leaves
`Alert` and `RefreshControl` unfinished, and backs others with browser APIs that a WebView lacks.
React Native mode replaces each of them with a denext implementation over
[`denext/mobile`](/docs/mobile), inside the Capacitor shell and in a browser. The replacement is
per module inside the installed react-native-web, so `import { Keyboard } from "react-native"`,
a deep `react-native/Libraries/…` import and react-native-web's own components (its `FlatList`
builds a `RefreshControl`) all get it. Names you do not use are still tree-shaken away, and
every other export is react-native-web's.

### Lists

`FlatList`, `SectionList` and `VirtualizedList` are replaced the same way. They run on denext's
`VirtualList`, built over the app's own react-native-web `View`, `StyleSheet` and
`RefreshControl`. `@shopify/flash-list` and `@legendapp/list` (its React Native entry) resolve
to denext's shims too. `inverted` is a logical reversal, `scrollToIndex` is exact, and sections
have sticky headers. `reactNative: { lists: "library" }` keeps every library's own engine.
The compatibility table and the gaps are in [Lists & scrolling](/docs/lists#react-native).

`expo-status-bar` resolves to a denext shim over the same `StatusBar`, so `<StatusBar
style="auto" />` sets the status bar in the shell and follows the page's color scheme.

What stays out of reach of a WebView:

- **Screen readers.** No web API says whether VoiceOver or TalkBack is running, so
  `AccessibilityInfo.isScreenReaderEnabled()` and its `screenReaderChanged` event come from
  denext's `DenextAccessibility` plugin in the shell (`denext mobile add accessibility`); in a
  browser, and in a shell without the plugin, it resolves `false`. Bold text and grayscale have
  no web signal and read `false`.
- **Keyboard frames on the web.** In a browser the visual viewport changes only once the
  keyboard is up, so the `Will` events arrive late there; the shell's `@capacitor/keyboard`
  reports before the animation.
- **`AppState` `memoryWarning`** is accepted and never emitted. `Linking.sendIntent()` rejects,
  and `Linking.openSettings()` rejects where nothing can open the settings (a browser, the
  Android shell without `denext mobile add permissions`).
- **`ActionSheetIOS.dismissActionSheet()`** is accepted and closes nothing, and the sheets'
  tint colors are not applied.

### Scroll snapping

react-native-web implements `pagingEnabled` only. React Native mode adds the rest of React
Native's snap props to `ScrollView`, and `FlatList` / `SectionList` / FlashList / LegendList
pass them to `VirtualList`'s `scrollSnap` ([Lists & scrolling](/docs/lists#scroll-snapping)):

| Prop                                                 | What it does                                                                                                  |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `snapToInterval`                                     | A snap point every interval px (a carousel's item width plus its gap)                                         |
| `snapToAlignment`                                    | Where each interval-wide slot meets the viewport: `"start"`, `"center"`, `"end"`                              |
| `snapToOffsets`                                      | Snap points at these offsets (wins over `snapToInterval`); `snapToStart` / `snapToEnd` add the content's ends |
| `decelerationRate="fast"`, `disableIntervalMomentum` | A fling stops at the next snap point (`scroll-snap-stop: always`)                                             |

They are CSS scroll snap (`scroll-snap-type: x mandatory`, and an invisible marker per snap point
near the viewport), so the fling itself stays the platform's native scroll and ends on a snap
point with no JavaScript per frame. `decelerationRate` changes nothing else: the momentum curve is
the platform's. A virtualized list whose scroll space is scaled (past about 8M px) does not snap.

### Text size

The OS text size reaches React Native's font scaling through `denext/mobile`'s font scale
(`denext mobile add accessibility`, [Text size](/docs/mobile#text-size)). A `Text` draws its
`fontSize` and a numeric `lineHeight` times the factor, React Native's default 14 px for an
outer `Text` without a size, while an inner `Text` without one inherits the scaled size;
`allowFontScaling={false}` opts out and `maxFontSizeMultiplier` caps it.
`PixelRatio.getFontScale()` and `useWindowDimensions().fontScale` report the factor and follow
changes. The factor is what the page still has to apply: the whole Dynamic Type factor in the iOS
shell (WKWebView ignores Dynamic Type), usually 1 in the Android shell (its WebView already zooms
all text by the system font scale, which `allowFontScaling={false}` cannot undo), 1 in a browser.

### Route announcements

Screen readers hear each screen change: the stack and tab navigators (React Navigation's and Expo
Router's, drawn by `denext/navigation`) and the drawer read the new screen's `title` into an
`aria-live` region, as VoiceOver and TalkBack announce a native screen change. The first screen is
not announced.

### `Platform.OS` in the shell

`Platform.OS` is `"web"` inside the iOS and Android shells too. React Native code branches on
`Platform.OS` to choose between a native module and a DOM code path, and inside a WebView only the
DOM path exists:

- react-native-web itself: its vendored `NativeAnimatedHelper` and `NativeEventEmitter` require a
  native module when `OS` is `"ios"` or `"android"`, and its `FlatList` turns on
  `removeClippedSubviews` for `"android"`.
- Libraries: Reanimated computes `IS_WEB` from `Platform.OS` at load time and uses its JS
  implementation only then; Gesture Handler's `findNodeHandle` and handler tags take their web
  path on `"web"`; `expo-modules-core` reads `process.env.EXPO_OS`, which the build defines as
  `"web"`.

Reporting `"ios"` or `"android"` would send all of these to native modules that do not exist.
To tell the shell apart, read `Platform.constants.denextShell` (or `runtimePlatform()` from
`denext/mobile`): `"ios"`, `"android"`, `"desktop"` or `"web"`. `Platform.Version`,
`Platform.isPad` and `Platform.constants` (`osVersion`, `systemName`, `interfaceIdiom`, and
`reactNativeVersion`, the React Native release React Native mode is measured against) also
describe the device.

`Platform.select(spec)` picks, in order:

1. `spec.web`, everywhere, as react-native-web does (`web` code is DOM code, and the shell is a
   DOM);
2. inside the iOS or Android shell, the shell's own key, `spec.ios` or `spec.android`, as React
   Native on that device would; in a Deno Desktop window, the host OS's key, `spec.macos`,
   `spec.windows` or `spec.linux`, as `react-native-macos` / `react-native-windows` would (when
   the runtime reports the OS: `Platform.constants.os`);
3. `spec.default`.

So `Platform.select({ ios: 44, android: 56 })` is 44 in the iOS shell and 56 in the Android
shell instead of `undefined`, while a `web` key still wins. `spec.native` is never picked (it
names React Native's native renderer, which a WebView lacks), a browser picks neither the shell
nor the desktop keys (there `select` behaves exactly as react-native-web's), and Deno Desktop
never picks `ios` or `android`. `Platform.constants.denextDesktop` is true in a Deno Desktop
window.

### Safe areas

React Native mode's SPA shell defaults the viewport to `viewport-fit=cover`, so the page runs
under the status bar, notch and home indicator as a React Native app does, and the insets are
real rather than 0. Both inset consumers read `denext/mobile`'s inset source (Capacitor 8's
injected `--safe-area-inset-*` on Android, where Android WebView before 140 reports wrong
`env()` values, else `env(safe-area-inset-*)`):

- React Native's `SafeAreaView` pads with it in CSS, so it is right on the first frame.
- `react-native-safe-area-context`'s web provider reports `useSafeAreaInsets()` from
  `denext/mobile` (clamped to the provider view, with its frame), so the package's
  `SafeAreaProvider`, `useSafeAreaInsets`, `useSafeAreaFrame` and `SafeAreaView` all follow it.
  The provider reports the measured insets in its first `onInsetsChange`, so its children never
  render once with zeros.

A viewport meta of your own in `spa.head` replaces the default (keep `viewport-fit=cover` in it),
and `reactNative: { rootStyle: false }` drops the default together with the root style.

## Reanimated and worklets

Reanimated 4 runs on the web through its own web build: every worklet is plain JavaScript on the
page's main thread. What it still needs from its Babel plugin (`react-native-worklets/plugin`)
is two properties on each worklet function: `__closure`, the values the worklet captures, and
`__workletHash`. `useAnimatedStyle`, `useDerivedValue`, `useAnimatedProps`,
`useAnimatedReaction` and `useAnimatedScrollHandler` use the closure as their dependency list.
Without it, `useAnimatedStyle` throws in dev when it has no dependency array, and in production
the hooks never re-run when a captured value changes.

React Native mode adds those two properties at build time, with no Babel. It finds worklets
the way the plugin does:

- functions with a `'worklet'` directive, and every top-level function of a file that starts
  with `'worklet'`;
- the callbacks of Reanimated's hooks, animation callbacks (`withTiming`, `withSpring`,
  `withDecay`, `withRepeat`) and scheduling functions (`runOnUI`, `scheduleOnUI`, …);
- gesture-handler builder callbacks (`Gesture.Pan().onUpdate(…)`), its v3 hooks
  (`usePanGesture({ onUpdate })`) and layout animations' `.withCallback(…)`;
- a name passed to one of those, when it names a function or an object of handlers declared
  in the same module (`const updater = () => …; useAnimatedStyle(updater)`).

It runs on your source and on node_modules (libraries built on Reanimated ship their worklets
untransformed, and Metro transforms them too). It runs only on modules that import
react-native-reanimated, react-native-worklets or react-native-gesture-handler or contain a
`'worklet'` directive. Code written for Metro therefore needs no changes:

```tsx
const offset = useSharedValue(0);
// No dependency array: `factor` (React state) is in the closure, so the style re-runs when
// it changes.
const style = useAnimatedStyle(() => ({ transform: [{ translateX: offset.value * factor }] }));
const pan = Gesture.Pan().onUpdate((e) => {
  offset.value = e.translationX;
});
```

When the build cannot see the worklet a hook reads, it prints a warning at the file and line.
This happens when the argument is the result of another call, such as
`useAnimatedStyle(useCallback(…))`. Pass the function inline, give it a `'worklet'` directive,
or add a dependency array: `useAnimatedStyle(fn, [dep1, dep2])`. An argument that comes from a
parameter or an import is assumed to be a worklet made elsewhere.

Not covered: worklet class methods and worklet classes (`__workletClass`), and context objects
(`__workletContextObject`). On the web these run as ordinary JavaScript, and nothing reads the
plugin's data for them. `runOnUISync` and `executeOnUIRuntimeSync` throw on the web
(Reanimated's own behaviour).

### Animations on the compositor

Reanimated's web build animates with a `requestAnimationFrame` loop on the page's main thread:
each frame it advances the animation, re-runs the style updaters that read it and writes inline
styles, so a busy thread (a long render, a large JSON parse) stops the motion. React Native mode
moves the common declarative animations to the Web Animations API instead, which the browser
runs on its compositor thread when only `transform` and `opacity` change:

- a shared value assigned an animation (`sv.value = withTiming(1)`) whose every reader is a
  `useAnimatedStyle` that maps it to `transform` / `opacity` (other keys of those styles may be
  present if they do not change);
- an animation the style returns itself
  (`useAnimatedStyle(() => ({ opacity: withTiming(visible ? 1 : 0) }))`) on those two keys;

for `withTiming`, `withSpring`, `withDelay`, `withSequence` and `withRepeat` trees, including a
`withRepeat` that runs forever (a spinner started in a `useEffect` is taken over once its style
mapper registers). The build simulates the animation on a copy at 60 Hz, samples the style
updaters at each frame and plays the samples as keyframes; your code does not change. Reading
`sv.value` meanwhile returns the interpolated value, completion callbacks fire when the
animation ends, and assigning the shared value again (or `cancelAnimation`) stops it where the
compositor has it. When another input of the style changes mid-animation, or a style starts or
stops reading the shared value, the animation goes back to Reanimated's loop at the same point.
In headless Chromium, such an animation kept drawing (26 distinct frames) through a 500 ms
main-thread block, and the same animation on Reanimated's loop drew none
(`tests/e2e/reanimated.e2e.test.ts`).

Everything else stays on Reanimated's loop, unchanged: a shared value that a `useDerivedValue`,
`useAnimatedReaction` or `useAnimatedProps` also reads, a style key other than `transform` /
`opacity` (width, colors), `withDecay` / `withClamp` / a custom animation, a callback on a
nested animation, gesture callbacks and `useFrameCallback` (they are main-thread worklets by
nature), and views that are not DOM elements. `globalThis.__DENEXT_REANIMATED_WAAPI = false`
turns the pass off. It patches Reanimated 4's own web modules (`lib/module`); a version whose
internals differ is left as it is and keeps its loop.

Layout animations (`entering={FadeIn}`, `exiting`, `layout={LinearTransition}`) are CSS
animations in Reanimated's web build already, so their `transform` / `opacity` keyframes run on
the compositor too.

`LayoutAnimation.configureNext` (a no-op in react-native-web) animates the next commit: views
that moved glide from their old position (a transform, on the compositor), created views animate
in and deleted views animate out by the config's `property` (`opacity`, `scaleX`, `scaleY`,
`scaleXY`), with its `duration`, `delay` and `type` (`spring` as a sampled spring curve). Views
that change size snap to the new size; a page with more than 3,000 elements is not animated.

**Performance.** A worklet on the web is still main-thread JavaScript, sharing the thread with
React, layout and your other code. For a simple transition (a fade, a slide, a press state), a
CSS transition or `ViewTransition` is cheaper than a Reanimated animation. Keep Reanimated for
gesture-driven and interruptible motion, and animate `transform` and `opacity` where you can.

## Images

`require("./logo.png")` and `import logo from "./logo.png"` resolve to the emitted file's URL,
which react-native-web's `<Image source={…}>` accepts. Resolution variants work as in Metro:
next to `logo@2x.png` and `logo@3x.png` (with or without a plain `logo.png`),
`require("./logo.png")` bundles every variant and is the URL of the one this screen wants, picked
by React Native's rule: the smallest scale at or above the device pixel ratio, else the largest.
The import is still a URL string, and it is picked when the module loads (a window moved to a
screen of another density keeps its first pick). Libraries' own image variants (React
Navigation's back icon) are picked the same way.

The list is `EXPO_SHIMS` in `denext/expo/manifest`. A few things to know:

- **Synchronous APIs.** Some Expo APIs are synchronous because they run over JSI. The
  Capacitor bridge is asynchronous, so `expo-secure-store`'s `getItem` / `setItem` are not
  provided (use the `…Async` forms), and `expo-file-system`'s sync calls act on an index the
  shim keeps and reach the files in the background (see its row).
- **The app config.** `expo-constants`' `expoConfig` (and `expo-updates`' server URL, and
  `expo-linking`'s scheme) come from `globalThis.__DENEXT_EXPO_CONFIG__`: set it to the
  `expo` object of your app config before the bundle runs, for example in `spa.head`:
  `<script>globalThis.__DENEXT_EXPO_CONFIG__ = {"name":"My app","scheme":"myapp"}</script>`.
- **Capabilities.** Inside the Capacitor shell each backed call needs its plugin installed:
  `denext mobile add <capability>` (haptics, clipboard, share, secure-store, push, …).
- **`expo-sqlite`** runs natively through `@capacitor-community/sqlite` (`denext mobile add
  sqlite`). On the web it needs the official engine installed in the app: `npm install
  @sqlite.org/sqlite-wasm` (denext ships no npm runtime dependency; without it, opening a
  database fails with an error naming the package). The build emits the engine's module and
  `sqlite3.wasm` as assets, and the database runs in a worker on the engine's `opfs-sahpool`
  VFS: persisted to the Origin Private File System, with no COOP/COEP headers needed (Expo's own
  web build uses the engine's `"opfs"` VFS, which needs a cross-origin-isolated page and
  otherwise never opens the database). Where OPFS is unavailable, or another tab of the origin
  holds the pool, the database is in memory for the session. The same functions are
  `openSqlite` / `deleteSqlite` in [`denext/mobile`](/docs/mobile).

## Maps

`expo-maps` (and `react-native-maps`) draw Apple Maps or Google Maps as native views, which a
web view does not have. In React Native mode `expo-maps` resolves to a
[stand-in](#expo-apis): the import works, the enums and the location-permission calls are real,
and each map view renders a labelled "Map unavailable" box and warns once in the console.

For a real map, give the screen a web map of its own in a `.web.tsx` file beside it (the
platform-file rule picks it up in React Native mode, and Metro keeps using the native file).
[MapLibre GL JS](https://maplibre.org/) and [Leaflet](https://leafletjs.com/) both work in
the Capacitor shell and the browser. Install one in the app (`npm install maplibre-gl`) and
mount it in an effect:

```tsx
// app/map.web.tsx: the web twin of app/map.tsx, which uses expo-maps
import { useEffect, useRef } from "react";
import { View } from "react-native";
import maplibregl from "maplibre-gl";
import "maplibre-gl/dist/maplibre-gl.css";

export default function MapScreen() {
  const box = useRef<HTMLDivElement | null>(null);
  useEffect(() => {
    const map = new maplibregl.Map({
      container: box.current!,
      style: "https://demotiles.maplibre.org/style.json",
      center: [-122.42, 37.77],
      zoom: 11,
    });
    new maplibregl.Marker().setLngLat([-122.42, 37.77]).addTo(map);
    return () => map.remove();
  }, []);
  return (
    <View style={{ flex: 1 }}>
      <div ref={box} style={{ flex: 1 }} />
    </View>
  );
}
```

The same pattern covers `@expo/ui`'s SwiftUI and Jetpack Compose views: their stand-ins render
the children with web layout so a screen loads, and a `.web.tsx` twin gives it a web UI.

## Durable storage

`@react-native-async-storage/async-storage` and `react-native-mmkv` resolve to denext stand-ins
over `denext/mobile`'s durable key-value store ([Durable storage](/docs/mobile#durable-storage)).
Their own web builds keep everything in `localStorage`, which iOS and Android may clear from a
WebView when the device runs low on space; in the Capacitor shell the stand-ins write a SQLite
file in the app's data folder instead (`denext mobile add storage`), on Deno Desktop the
runtime's SQLite, and in a browser IndexedDB.

- **AsyncStorage**: the whole 2.x API (`multiGet`, `multiSet`, `mergeItem`, `getAllKeys`,
  `clear`, the callbacks, `useAsyncStorage`) and 3.x's `getMany` / `setMany` / `removeMany` /
  `createAsyncStorage`. Each batch is one native call. The first call copies what an earlier
  build wrote to `localStorage` into the durable store, once.
- **MMKV** is synchronous and a WebView has no synchronous native call, so reads come from an
  in-memory copy: seeded at once from `localStorage` (MMKV's web format, which every write
  keeps), then reconciled with the durable store in the background. Writes return at once and
  reach the durable store a moment later. After the OS cleared the WebView's storage, a read
  misses those keys until `mmkvReady()` (a denext addition) resolves, then the value-changed
  listeners fire and the `useMMKV*` hooks re-render; await it before the first render when that
  matters. Encryption is refused: keep secrets in `expo-secure-store`.

`denext mobile doctor` warns when AsyncStorage or MMKV is installed without a durable native
store, and about app code that keeps data in `localStorage` or IndexedDB itself.

## Community packages

Popular React Native libraries call native modules or views a WebView does not have: some fail
the build (Flow source, `requireNativeComponent`), some render nothing, and some throw when
used. React Native mode resolves each one below to a denext implementation with the same API,
so the app's imports run unchanged. It is on for every listed package; turn one off with
`reactNative: { aliases: { "<package>": false } }` to get the real library back (a typo fails
config validation, with the closest name).

How each kind is provided:

- **Runtime stand-ins** are prebuilt denext modules, sharing the app's denext instance, built
  over `denext/mobile` (so they need the listed `denext mobile add` capability in the Capacitor
  shell) or over web platform features.
- **The navigators** (`@react-navigation/native-stack`, `@react-navigation/bottom-tabs`) keep
  the real package and replace only `createNativeStackNavigator` / `createBottomTabNavigator`
  with `denext/navigation`'s. `@react-navigation/drawer` is a denext drawer over React
  Navigation's `DrawerRouter`. Both are built from the app's own `@react-navigation/native`.
  expo-router's own `Stack` / `Tabs` are swapped separately ([expo-router](#expo-router)).
- **`react-native-keyboard-controller`**'s `useReanimatedKeyboardAnimation` /
  `useAnimatedKeyboard` return real Reanimated shared values when `react-native-reanimated` is
  installed, and plain `{ value }` holders otherwise.
- **`.svg` imports** become components (Metro's react-native-svg-transformer, restated) when
  the app has both `react-native-svg` and `react-native-svg-transformer`: `import Logo from
  "./logo.svg"` renders the file through react-native-svg's `SvgXml`, props passed on. CSS
  `url()`s keep the file.
- **NativeWind v4**: see the [recipe](#recipe-nativewind-v4).

`denext migrate --from expo` lists the app's aliased packages and adds their capabilities to
the `denext mobile add` command it prints.

## Other native-only packages

Packages with no web build and no denext shim or alias (native modules, Nitro/JSI packages)
still need a web replacement of your own. A TurboModule / Fabric codegen package loads as it
is, because of the [codegen entry points](#what-reactnative-does): its spec's top-level
`getEnforcing` no longer throws, and a `requireNativeComponent` view renders its children unless the view type is registered natively, so the
package fails only when its native module is actually used. It still needs a replacement if
the web build calls into that module, unless the app ships that module as a Capacitor plugin of
the same name ([Your own native code](/docs/native-code)). Two kinds fail earlier, before any use: a package whose
`main` is Flow source (a parse error at build time), and an Expo module that calls
`requireNativeModule` at the top level (it throws at import, which stops the bundle). The
listed [Expo shims](#expo-apis) and [community packages](#community-packages) cover the common
ones; `denext migrate --from expo` names the native-only packages it finds. Two ways to
replace one:

- Add a `.web.ts` beside the module that imports it, exporting a web implementation. The
  platform-file rule picks it up.
- Map the package to a shim in `deno.json`'s `imports`, for example
  `"react-native-nitro-markdown": "./web-shims/nitro-markdown.ts"`.

## Recipe: uniwind and Tailwind

uniwind styles React Native components with Tailwind classes. Its web
setup is specific to the app, so denext does not build it in. What it takes:

1. Compile the Tailwind input with denext's Tailwind integration:
   `tailwind: { input: "./global.css", output: "./global.gen.css" }` in `denext.config.ts`,
   and import `global.css` from the web entry.
2. Run `uniwind generate-artifacts` once for any themes beyond the default, and commit the
   generated CSS it writes.
3. Two importer-sensitive aliases: `react-native` imported from anywhere except uniwind's own
   files resolves to uniwind's web components (`uniwind/dist/module/components/web/index.js`),
   and react-native-web's `StyleSheet` importing `./createOrderedCSSStyleSheet` gets uniwind's
   version from the same directory.

denext's config has no seam for importer-sensitive aliases yet. Until it has one, apply step 3
with [`denext patch`](/docs/patches): patch `src/build/react-native.ts` so the `react-native`
resolver returns uniwind's index when the importer is outside `/uniwind/dist/`, and
`src/build/next-compat.ts`'s app resolver so the `./createOrderedCSSStyleSheet` import from
`react-native-web/dist/exports/StyleSheet` returns uniwind's file.

## Recipe: NativeWind v4

NativeWind v4 styles React Native components with Tailwind classes through
`react-native-css-interop`. With `nativewind` installed, React Native mode runs the app's own
JSX through `nativewind/jsx-runtime` (what NativeWind's Babel preset does with
`jsxImportSource: "nativewind"`), so `className` on a `View` or `Text` becomes class names
react-native-web renders. Packages keep the plain runtime. The Tailwind CSS is compiled by
Tailwind 3's CLI (NativeWind v4 targets Tailwind 3), the step NativeWind's Metro plugin runs:

1. Install `nativewind` and `tailwindcss@3`, and keep NativeWind's `tailwind.config.js` (its
   `presets: [require("nativewind/preset")]` and `content` globs) and `global.css`
   (`@tailwind base; @tailwind components; @tailwind utilities;`).
2. Compile it: `npx tailwindcss -i global.css -o src/nativewind.css` (add `--watch` beside
   `denext dev`, or run it from a `deno.json` task before `denext build`).
3. Import the output once from the web entry or the root component:
   `import "./nativewind.css";`.

`metro.config.js`'s `withNativeWind` and `babel.config.js`'s `nativewind/babel` are not used.
`reactNative: { aliases: { nativewind: false } }` turns the JSX runtime off.
