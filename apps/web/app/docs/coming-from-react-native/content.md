denext is a web framework (Next.js's App Router on Deno) that also ships to phones: the app is
exported to static files and a [Capacitor](https://capacitorjs.com) shell runs it in the
system WebView. [`denext/mobile`](/docs/mobile) is the client runtime for that shell, and
`denext mobile` installs the native side. Components render to the DOM, not to native views.

There are two ways in:

- **New code, or a web app going mobile:** write a denext app and add the Capacitor shell.
  Start with the [Mobile quickstart](/docs/mobile#quickstart).
- **An existing Expo / React Native app:** `denext migrate --from expo` builds the app's own
  source for the web through react-native-web, with the `expo-*` packages resolved to denext
  shims. See [React Native / Expo apps](/docs/react-native#migrating-an-expo-app).

The table says which one each row is about.

## What a WebView changes

**The rendering model.** A React Native component becomes a native view laid out by Yoga. A
denext component becomes DOM that the WebView lays out and paints with CSS. The whole UI is one
web page: a screen is a route, a modal is an element, and anything the browser can render (CSS
effects, SVG, canvas, a code editor, a terminal) is available without a native module. What is
lost is the native widget itself: the native navigation stack, native lists, the UI-thread
animation and gesture runtimes, and platform controls that have no web equivalent.

**Threads.** Your JavaScript, style and layout share the page's main thread. The WebView
scrolls and animates CSS `transform` and `opacity` off that thread, so prefer those for
motion and keep long lists virtualized; there is no second thread for worklets.

**Performance expectations.** On iOS, WKWebView holds up well for the app denext's mobile work
is measured against (T3 Code's web UI). On Android only an emulator has been measured so far:
the Capacitor build of that app started in less than half the time of its React Native build
and used less memory, but scrolled a long list clearly worse. The emulator composites on a
weak host GPU, which costs a WebView more than native views, so this is not settled until a
real-device run. The numbers are in
[REACT-NATIVE-EXPO.md](https://github.com/Brainwires/denext/blob/main/REACT-NATIVE-EXPO.md)
(gap 5) and the current platform status is on [the mobile page](/docs/mobile).

**One codebase for the web too.** The same export runs in a browser, in the Capacitor shell and
in a [Deno Desktop](/docs/desktop) window. Most `denext/mobile` functions fall back to a
browser API on the web; the native-only ones say so (`requestPushPermission` resolves
`"unsupported"`, the Live Activity functions reject with code `unsupported`), so shared code
can check instead of branching per platform.

## When to stay on React Native

Native rendering is out of scope for denext: Capacitor and the WebView are the mobile story
([Policies](/docs/policies)). Stay on React Native when your app needs what only native views
give:

- screens whose value is the native feel on Android (long, fast-scrolling lists, native
  navigation transitions), at least until Android is measured on a real device;
- UI-thread animations and gestures (Reanimated worklets, gesture-driven interfaces);
- synchronous native APIs over JSI (MMKV, the sync SQLite API, Nitro modules, camera frame
  processors), which an async Capacitor bridge cannot provide;
- a large investment in native modules and screens you would have to rewrite as Capacitor
  plugins or web components.

## Migrating

To build an existing Expo or React Native app with denext, run `denext migrate --from expo`
in the app: it writes the `deno.json`, a React Native mode `denext.config.ts` and a
`capacitor.config.ts`, changes no source, and reports which `expo-*` packages are shimmed,
which packages are native-only, and the `denext mobile add` command for the capabilities you
use. The details are on [React Native / Expo apps](/docs/react-native), and the per-package
shim status in the [Expo APIs](/docs/react-native#expo-apis) table.
